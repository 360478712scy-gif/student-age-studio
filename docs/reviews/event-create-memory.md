# 大型模组创建与保存性能修复

## 问题与范围

用户在 Windows 1.4.8 中填写新事件后点击「创建」，页面显示 `STATUS_BREAKPOINT`；后续补充模组有 50 万句对话，各处保存都卡，举例只改送礼配置。该截图不能单独确定浏览器进程的崩溃原因。当前修复以已发布的 `0b15819` 为基础。

## 已确认的问题与修改

- 创建弹窗和提交都调用旧事件的入口查找。空的新事件没有可查找的归属，却会访问所有对话。新建时直接保留默认入口或手选入口；已有事件仍按原顺序查找，并先过滤不可见和内部行。
- 创建后的归属同步只判断行是否存在时，仍访问每个行对象。现在复用图分析已有的 ID 集合，保留共享、显式保留和锚定归属。
- 创建后自动编号对空事件遍历所有对话。没有任何可编号的归属行时直接返回，正常事件的分支顺序不变。
- 归属结果及反向连接的构造不再创建整表的中间键值对数组；结果与旧算法保持一致。
- `validate_map` / `repair_map` 和分段记录解析原有 250,000 行限制使 50 万句被当成格式错误。本地读取另有 96 MiB 预判拒绝。移除这些本地门槛，保留真实格式、编号、重复键及尾行检查；实际内存不足返回明确读取错误，HTTP 请求限制保持。
- 首次加载原先创建一份整表行副本并重复校验。现在单遍校验，完整行复用，只复制编号不一致的行。50 万句全部保留，ID 校验调用由 2,004,008 降到 501,002；并行负载下总耗时没有证明提速，不作首次加载已流畅的结论。

43,827 行冷目录的旧入口查找实测创建了所有行的代理对象，同步调用增加约 66 MiB 堆内存，没有加载正文。这个数字是隔离测量，不是反馈者电脑的崩溃记录。

## 保存的独立瓶颈

- 通用剧情保存即使只改空事件或单句效果，也深复制完整配置并重复计算归属。简单编辑改用逐表浅快照，实际改行仍独立复制；删除、编号迁移、前提、托管 BGM 和外部用途等复杂路径保留完整依赖及深快照。归属缓存只留一个模组的一份结果，绑定实时修订、全部图字段、前次归属、编号范围和锚定行；真实写入文件摘要吻合后才推进修订。
- 工作态送礼外部对话夹在同步前独立复制，避免旧快照同时改变而漏写解绑；相关事件有绑定或既存夹有绑定时按需读取送礼表。编号不一致将修复并走全依赖、深快照，级联关联表仍写入。两项由独立复核发现、真实磁盘用例修复前失败及修复后通过。
- 剧情保存的社交效果清理无条件扫描每个对话对象。Remote 改为读取摘要字段；Indexed 预筛字段键，只解码候选行，草稿新增、删除、转义字段和原有真假值语义保持一致。
- 剧情保存重复解析相同的提交和已保存快照。正常路径复用两个解析结果；等待正文期间已保存基线发生变化时仍重新解析最新基线。保存期间的后续编辑和失败后的编号映射都保留。
- 社交效果首次初始化后的数组操作会落在 Remote setter 已复制的旧对象上。初始化后重新从行代理读取跟踪对象，重复保存正确清理生成的效果，保留手写效果。
- 公共文件修订检查把 JSON 解析的 96 MiB 限制用于无关文件，导致大型 TalkCfg 旁的送礼保存返回 HTTP 413。修订摘要本来按 1 MiB 分块读取，现在只保留路径检查和变更检测；没有改目标表的解析或 HTTP 请求限制。
- 工坊根据字段 schema 自动预加载 TalkCfg 引用，送礼的 `talkId` 范围因此拉取整张对话表。改为需要选择对话引用时再读取，既有入口 ID 保留。
- 显式对话引用改用已有 `command-references` 接口，避免编辑表接口为了 `localRows` 再复制完整目录；真实读取失败仍可提示、重试。
- 插件小游戏不再在打开和保存重绘时构造每关三份全量对话选项。明确选择入口时读取目录，搜索和分页每次只渲染 80 条。
- JSON 编码回写送礼、人物等非图表时保留历史和保存基线，不再整理对话分支或重算归属。对话、选项、事件的写入仍走原图处理路径。
- 保存依赖的 `readable_maps` 也有整表临时行副本与重复编号检查。改成单遍键/记录检查，返回原生行不修改编号，让既有修复、备份和级联逻辑处理；零键与坏表规则保持。
- 场景找不到入口路径时，前驱恢复会遍历整表并长期保留每行代理。路径查找改读 Remote 的六个路由元数据字段；正文与人物动作重建仍使用原模型和所得路径。没有把实际 41 s 编辑延迟全部归因于此。
- 载入已保存顺序、初始图遍历和合并条件引用目录仍逐行访问对话，保留全表代理。顺序只检查编号存在，图遍历只读连接元数据，引用目录改为按 ID 读取的合并视图；完整目录、当前行、原版回退及未知字段保留。
- 只改已有事件标题也进入完整剧情归一化。新增严格快路径：项目修订和分段会话校验后，事件编号集合完全相同、记录编号正确，只改变顶层 `title` 和已有 `studioSocial.title` 字符串标签、其他 JSON 字段及类型完全一致时，通过既有原子事务只写事件表。元数据遗漏/新增/删除、其他字段差异、记录新增/删除/修编号或额外提交都回原流程；省略原标题保留原标题，备份、外部修改检测、失败回退和旧对话页保留。

50 万句、103,366,892 字节的隔离 TalkCfg 旁，送礼字段修改和新增行的真实 HTTP 保存分别约 14 ms / 18 ms；暖保存未读取或解析 TalkCfg，冷摘要只分块哈希一次，约 79 ms。对话文件 SHA256、指纹均未改变，备份只包含改动表。这是 macOS 后端测量，不是 Windows UI 延迟。

同一 500,000 条完整样本、不带 `talkGeneration` 的隔离请求，macOS cProfile 的空事件保存 62.692→11.340 s，单句效果保存 64.378→18.451 s。前者只写事件表和编辑记录，对话字节不变；后者只写对话表，保留所有 500,000 行、正文、连接及未知字段。cProfile 有额外分析开销，不能当成 Windows UI 等待时间，也不能代表下方真正分段模式的请求。

真实 103,366,892 字节、500,000 句的分段打开先后复现「对话文件过大」「对话表记录过多」。最终完整打开约 29.3 s，逐条 ID 和正文目录、首/中/末实际页读验证通过，源 SHA256 与文件指纹不变。这是 macOS 读取证据，不能替代 Windows 界面验收。

真实带 `talkGeneration` 的 50 万句保存另行验证：空事件 31.282→22.765 s，单句屏幕效果 56.857→26.469 s（Mac cProfile）。`SegmentService.saved` 约 3–4 ms，没有重新打开或构建 Generation；目录重建的初步怀疑已由调用计数排除。这轮修复针对保存依赖的整表副本。全量磁盘对照确认，只有指定效果改变，全部正文、nextTalk 和未知字段保留，无关 Gift/Option 字节不变。

真实 500,000 句、活动 `talkGeneration` 下的纯已有事件标题请求（1,000 个事件、87,280 字节），快路径保存约 24.8 ms（Mac、无 cProfile）。TalkCfg 读取、整表依赖读取和归属计算均为 0，事务只备份 EvtCfg；50 万句文件哈希、首/中/末旧页及不可变目录对象不变，修订正确推进。修复前同请求在首次 TalkCfg 读取处触发测试断言，因此只证明旧路径确实读取大表，不能把中断耗时当成完整保存的基线。

最终补测真实原生表单捕获的 1,002 个事件请求及其事务前原始事件文件：除顶层标题外，表单还更新旧 `studioSocial.title` 标签。旧严格守卫未命中，这个真实缺口已修复。相同捕获内容在真实 500,000 句活动 generation 的后端回放约 16.1 ms，直接 `TalkCfg Path.open`、解析、依赖读取和归属计算均为 0；只写/备份 EvtCfg，两标签完整写入、其他事件数据深等捕获目标、对话全字节哈希及旧页不变。这是 Mac 后端回放，最终扩展守卫后没有重新测量原生 UI 耗时。

## Windows 原生窗口

复用现有 Windows 11 ARM64 虚机（12 GB 内存，x64 Python 3.12.10 通过模拟运行）、原生 pywebview / WebView2 `154.0.4258.53` 与暖缓存。耗时不能直接代表客户的原生 x64 硬件。50 万句样本的送礼修改保存约 1.625 s，POST 533 ms；物品仓库保存约 718 ms，POST 369 ms。两段流程没有请求 TalkCfg，原表 500,000 条的字节 SHA256 不变。无页面异常、渲染进程崩溃或 ProcessFailed。

旧版的自动 Talk 引用请求实际返回 HTTP 400（250,000 行门槛），没有把 50 万句正文加载进渲染器；不能用它作旧版全正文内存基线。改用轻引用接口后，真实完整目录选择、保存通过，首次目录流程约 49.219 s，仍慢。

解除分段门槛后的候选窗口进入真正 Remote 模式：500,000 句目录、11 句正文；创建约 16.375 s，撤销/重做通过。首次冷加载执行约 168.1 s，另有启动排队约 162.7 s，不能称首次进入流畅。此阶段真实保存仍慢：空事件 UI 110.453 s / POST 86.784 s；效果 POST 204.935 s（180 s 观察门槛超时后原请求自然完成，没有再次提交）。两次均成功上盘、全量原文/连接/未知字段保留，没有 ProcessFailed。这些实际请求暴露了保存依赖读取的遗漏热点，随后修复 `readable_maps` 和场景路由代理。

下一候选源（app `ab70ae61`、Remote `2397b240`、server `8e09a167`）的两次同窗真实保存：标题 UI 104.375 s / POST 77.486 s；单句屏幕效果 UI 96.860 s / POST 79.987 s。真实请求体分别为 87,755 字节（仅事件表）和 448 字节（仅一条 talkPatch），没有重复提交。50 万句正文和 nextTalk 逐行验证、未知字段、无关表字节及事件标题均保留。窗口在保存之前的载入附近记录了一次 `RenderProcessUnresponsive`，没有崩溃页，但不能记为原生流畅性通过；两次后续写入成功只说明磁盘语义通过。

随后修复启动全表代理，app `d4e69345` / server `932a2297` 的最后一个原生窗口首次目录初始化约 132.797 s，Remote 500,000 句、11 句正文。真实表单 Apply 36.719 s、保存 UI 61.797 s / POST 47.522 s，原生窗口没有新增 ProcessFailed、页面异常或崩溃。事务只写 EvtCfg，对话 71,878,980 字节及 SHA256 `2da3873d05193464573f27227703b6cf9712d8acb998cec3d11258f74a0a2970`、无关表字节保持不变。

此请求因 `studioSocial.title` 同时变化而未走当时的纯标题守卫；它是最后双标签补丁的修复前原生数据，不能当成新快路径测量。实际请求、事务前/后文件和完整双字段差异用于上方最终后端回放。所有自有原生窗口均已关闭，没有重复提交或关闭其他进程树。

最终源码：app `d4e69345`、Remote `2397b240`、server `ccf646c6`、segments `cea5922b`。23 个运行时/测试文件已同步私有与公开源码并核对哈希；版本未改。

### 剩余性能边界

首次大目录读取、事件应用及实际修改剧情正文/分支的通用保存仍有明显延迟；当前不能宣布 50 万句编辑已整体流畅，也未复现反馈者原始 `STATUS_BREAKPOINT`。最新双标签补丁有真实捕获内容的后端回放证据，没有修后原生 UI 耗时。已消除送礼、物品及标签保存读取无关对话的热点，真实大表写入和前端快照的线性成本仍存在。

证据：`output/event-create-crash/first-owned-probe.json`、`event-empty-performance.json`、`save-front-remote-text-reused.json`、`fixed-summary.json`、`backend-save-profile/{baseline,fixed}-results.json`、`fixed-500k-read-results.json`、`final-save-native-summary.json`、`remote-load-order.json`、`frozen-native-title-summary.json`、`frozen-native-title-exact-event-diff.json`、`backend-save-profile/social-after-title-generation-results.json`。未拿到反馈者实际模组，不把隔离验证等同于其全部条件已覆盖。
